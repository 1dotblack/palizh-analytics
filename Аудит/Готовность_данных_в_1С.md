# Готовность данных в 1С

**Дата:** 2026-08-17  
**Для кого:** разработчик 1С, аналитик ERP, QA, ответственный за стенд B2B Palizh  
**Снимок платформы:** GitLab `main` @ **`ad55296`**.  
**Еженедельный аудит 1С (короткий):** [`Аудит_готовности_1С_2026-08-17.md`](Аудит_готовности_1С_2026-08-17.md).  
**Первая версия объёмов:** [`Чеклист_1С_данные_для_демо_и_тестирования.md`](../Техническая%20часть/Чеклист_1С_данные_для_демо_и_тестирования.md).

**Назначение:** единый список **что должно быть в 1С**, чтобы проверить витрину, ЛК и обмен с платформой. Не заменяет канон JSON ([`входящие/incoming-hooks.md`](../входящие/incoming-hooks.md)) и исходящие HTTP ([`1c-http-openapi.yaml`](../Техническая%20часть/1c-http-openapi.yaml)).

## 0. Что проверяем / чего не готовить как сценарий

| Можно проверять, если датасет готов | **Не** обещать / не готовить как pass |
|-------------------------------------|----------------------------------------|
| Каталог, дерево категорий, select-фильтры, цены B2B, остатки | Live-смена **статуса** заказа в ЛК (handler на платформе нет) |
| Создание заказа на платформе → «Заказ клиента» с тем же GUID | Автообновление **состава** заказа после правок в ERP |
| Номер заказа (`orderNumber`) в ЛК | Раздел «Документы» в UI ЛК (API есть, страницы нет) |
| Счёт через `sync.documents` / `get_documents` (проверка API) | Фильтр «Оттенки» на FE пока может быть на mock — **HEX в 1С всё равно нужны** |
| Претензия на существующий заказ (данные заказа в 1С) | Претензия / УКД / заявка как документы `sync.documents` |

## 1. Технические работы обмена (чеклист)

| № | Работа | Статус |
|---|--------|--------|
| A1 | Опубликован тестовый HTTP-сервис (контур B2B) | ☐ |
| A2 | Basic Auth; учётные данные переданы ответственному за стенд (**не** в git) | ☐ |
| A3 | Allowlist IP egress платформы → 1С | ☐ |
| A4 | 1С инициирует push каталога на `POST /exchange` (порядок — §1.1) | ☐ |
| A5 | `POST /post_orders`: «Заказ клиента» с **GUID = `externalGuid`**; ответ **201** `{ "orderNumber": "…" }` | ☐ |
| A6 | Повтор с тем же `externalGuid` → **409** или **201** с тем же номером (без дубля) | ☐ |
| A7 | `GET /get_documents?type=&guid=` отдаёт файл (счёт) | ☐ |
| A8 | `sync.documents` после счёта: `type: bill`, `relatedEntityType: order`, `relatedEntityGuid` = GUID заказа | ☐ |
| A9 | `sync.categories` — **только папки**, дерево через `parentGuid`, **не** SKU | ☐ |
| A10 | Inbound статусов заказа | ☐ **отложено** (нет handler; не включать в сценарий демо) |

### 1.1. Порядок событий каталога

```
sync.product-attributes
→ sync.product-types
→ sync.product-type-characteristics
→ sync.products
→ sync.stocks
→ sync.prices
→ sync.categories
→ sync.counterparties
```

Успех платформы: **HTTP 202**. Примеры полей — `incoming-hooks.md`.

## 2. Каталог: минимальный датасет

Ниже — **минимум для теста**. Можно больше; меньше — сценарии будут дырявыми.

### 2.1. Категории (`sync.categories`)

| Требование | Минимум |
|------------|---------|
| Корень | **1** (напр. «Клеи и герметики» или «Лакокрасочные») |
| Дочерние | **≥ 3** (напр. Герметики / Краски / Грунтовки) |
| `parentGuid` | Заполнен у детей |
| В payload | Только группы навигации, **без** номенклатуры |

**Pass:** `GET /api/categories` — дерево с детьми, не сотни «корней» с именами SKU.

### 2.2. Атрибуты фильтров

| `code` | Label (пример) | Опций ≥ |
|--------|----------------|---------|
| `worktype` | Типы работ | **3** |
| `surface` | Обрабатываемая поверхность | **3** |
| `special` | Специальные свойства | **3** |
| `tintingMethod` | Способ колерования | **3** |

Каждый тестовый товар в «цветной» и «обычной» категории — **≥ 1** заполненный атрибут.

### 2.3. Цвет: характеристики и номенклатура

Цвет — **характеристика** типа номенклатуры (HEX + название + RAL), не отдельный SKU на каждый оттенок.

| Сущность | Минимум |
|----------|---------|
| Тип номенклатуры с цветом | **1** |
| Характеристики цвета | **15**: **5 зелёных + 5 красных + 5 синих** (разный HEX, имя, RAL) |
| SKU в «цветной» категории | **≥ 15** (≥ 1 товар на каждый оттенок) |
| SKU в другой категории | **≥ 10** (поиск / пагинация без акцента на цвет) |

Ориентир HEX: зелёный `#1B5E20`…`#81C784`; красный `#B71C1C`…`#EF9A9A`; синий `#0D47A1`…`#90CAF9`.

На **платформе** (не 1С): 3 группы оттенков в админке + «Прочие». Без этого UI цвета может остаться на mock даже при правильной выгрузке.

### 2.4. Упаковка, цены, остатки

| Поле / факт | Минимум |
|-------------|---------|
| `unitsPerBox` > 1 | У **≥ 5** SKU (напр. 6 или 12) |
| Цены на пару товар+характеристика | `RETAIL`, `WHOLESALE`; `BOX` там, где есть коробка |
| Остаток > 0 | У большинства демо-SKU |
| Остаток = 0 | У **≥ 2** SKU |
| Архив / снят с пр-ва, остаток 0 | **≥ 1** (не в активной витрине) |
| «Снят», но остаток > 0 | **≥ 1** (доступен к заказу по правилам MVP) |

### 2.5. Контрагенты

| Сущность | Минимум |
|----------|---------|
| Активных контрагента с GUID | **≥ 2** |
| Соглашение / вид цены | По **1** на контрагента |
| Персональная скидка % | У **1** контрагента |
| Exclusive-номенклатура | **≥ 1** SKU только для контрагента A (опционально) |
| Учётка ЛК на стенде | Привязана к контрагенту A |

## 3. Заказ в 1С (результат обмена)

| Сущность | Минимум | Как проверить |
|----------|---------|---------------|
| Документ «Заказ клиента» | **≥ 1** с платформы | GUID документа = `externalGuid` платформы |
| Строк в заказе | **≥ 3** | Для претензии и состава в ЛК |
| Номер | заполнен | Ответ `orderNumber` → поле `number` в ЛК |
| Повтор `post_orders` | тот же GUID | Нет второго документа-дубля |

Риск с платформы: checkout может прислать `comment` / дату как строку `'null'` — в ERP не должно становиться «кривым» заказом без явной ошибки обмена.

## 4. Документы: что класть в 1С и куда привязывать

Коды `type` — enum платформы `DocumentType` (`ad55296`). Бизнес-привязка — ЧТЗ 02.

### 4.1. К заказу (`relatedEntityType: order`)

`relatedEntityGuid` = GUID «Заказ клиента» = `externalGuid`. Иначе документ не попадёт в карточку заказа.

| Документ | Код `type` | Когда появляется | Для теста обмена |
|----------|------------|------------------|------------------|
| Счёт на оплату | `bill` | После оформления / обработки | **Обязательно ≥ 1** на тестовый заказ |
| УПД | `upd` | После отгрузки | Желательно ≥ 1; часто `file: null` → `GET /get_documents` |
| ТТН | `ttn` | Если сформирована | Опционально |
| Паспорт качества (на партию) | `quality_passport` | По партии / отгрузке | Опционально; не путать с TDS на SKU |

В пакет заказа **не** класть акт сверки, договор, претензии, заявки.

### 4.2. К контрагенту (`relatedEntityType: counterparty`)

| Документ | Код | Для теста | Где в ЛК (когда появится UI) |
|----------|-----|-----------|------------------------------|
| Акт сверки | `reconciliation_act` | Опционально ≥ 1 (период + контрагент A) | Раздел **«Документы»**, **не** карточка заказа |
| Договор / ДС | `agreement` | Опционально | «Документы» / профиль |

Запрос акта из ЛК (async API) на текущем срезе **не считать готовым**; для проверки обмена достаточно push уже сформированного файла через `sync.documents`.

### 4.3. К номенклатуре (`relatedEntityType: product`)

| Документ | Код | Для теста |
|----------|-----|-----------|
| TDS | `tds` | Если файлы уже есть в 1С — 1–2 примера |
| MSDS / SDS | `msds` | То же |
| Паспорт безопасности (SKU) | `safety_passport` | То же |
| СГР | `sgr` | То же |
| Каталог линейки | `product_catalog` | По согласованию |
| Прочее | `other` | Только после согласования с продуктом |

Если файла нет в 1С — вне автоматизированного ЛК (менеджер). В примере `incoming-hooks.md` перечислены не все `type` (там в тексте в основном `agreement` / `upd` / `bill`) — ориентир по кодам: этот раздел и [`Чеклист_1С_sync.documents.md`](../Техническая%20часть/Чеклист_1С_sync.documents.md). В контракте выдачи иногда пишут `invoice` — в API код **`bill`**.

### 4.4. Чего в `sync.documents` быть не должно

| Сущность | Почему |
|----------|--------|
| **Претензия** и вложения клиента | MVP: карточка на платформе, статус «Отправлена». 1С и Mass Project статусы/УКД в ЛК не отдают |
| УКД, новая реализация, возврат по претензии | **Post-MVP**; отдельного `type` в enum нет |
| **Нестандартная заявка** | Не печатная форма; на платформе (сейчас UI-заглушка) |
| **Заявка на обучение** | Платформа, не 1С |
| **Заявка «стать клиентом»** | GUID заявки живёт в **карточке контрагента** (`sync.counterparties`), не как документ |

## 5. Статусы заказа (для будущего теста inbound)

На текущем срезе платформы **handler нет** — live-смену статуса не включать в демо. Ниже — что **должно быть в 1С как объекты ERP**, чтобы потом замкнуть обмен, и какие коды **не слать**, пока бэкенд не зафиксирует enum.

### 5.1. Канон ЧТЗ — ровно 6 статусов ЛК

| № | Статус в ЛК | Объект / событие в 1С |
|---|-------------|------------------------|
| 1 | Обрабатывается | Документ **«Заказ клиента»** создан |
| 2 | В производство / производится | **Заказ на производство** |
| 3 | Готов к сборке | **Реализация** есть, **расходный ордер не проведён** |
| 4 | Готов к отгрузке | **Расходный ордер проведён**, партия скомплектована |
| 5 | Отправлен | Задание на перевозку / маршрут / отправка ТК |
| 6 | Завершён | Доставка завершена или заказ закрыт |

Не отдельные статусы заказа: трек ТК, водитель, точки маршрута — **детали доставки** внутри «Отправлен».  
Не статус заказа: оплата (`paid` / `unpaid`) и состояние синка платформы (`integrationSyncState`).

### 5.2. Коды для inbound — не разъехаться

Рабочий ориентир (OpenAPI публичного API):  
`processing` → `in_production` → `ready_for_assembly` → `ready_for_shipping` → `shipped` → `completed`.

| Не использовать | Почему |
|-----------------|--------|
| `new`, `awaiting_payment`, `paid`, `shipping` | Чужая шкала в старом чеклисте заказов; `paid` — оплата, не статус заказа |
| `ready_for_picking` / `ready_to_ship` | Другие имена в маппинге vs OpenAPI |
| `preparing_for_shipping` | Есть в enum бэка (**7-е** значение), в ЧТЗ шести статусов нет |

Имя `event` (черновик `sync.order-status`) **не зафиксировано**. Пока handler нет, любой такой POST на `/exchange` даст **400**.

Для теста **данных** в ERP достаточно уметь провести тестовый заказ по цепочке документов §5.1; выгрузку статуса на платформу — после согласования с бэкендом.

## 6. Матрица: сценарий теста → что должно быть в 1С

| Сценарий на платформе | Нужно в 1С |
|-----------------------|------------|
| Витрина / категории | Дерево §2.1 |

| Корзина, кратность | `unitsPerBox` + BOX/RETAIL |

| Обучение | **Не нужно** в 1С |
| Live-статусы | **Не готовить сценарий** на этом срезе |

## 8. Критерии готовности данных (pass / fail)

| № | Проверка | Pass |
|---|----------|------|
| E1 | `GET /api/categories` | 1 корень + ≥3 детей; имена — группы, не SKU |
| E2 | `GET /api/products?categorySlug=<цветная>` | ≥15 позиций |
| E3 | Цены для контрагента A | Непустые `amount` / персональные поля |
| E4 | Checkout на стенде | В 1С заказ, GUID = `externalGuid` |
| E5 | ЛК | У заказа заполнен `number` |
| E6 | Повтор `post_orders` | Нет дубля документа |
| E7 | `sync.documents` `bill` | Метаданные на платформе / download через API |

**Fail по данным:** плоский список категорий из товаров; пустые цены у B2B; `post_orders` 5xx / нет номера; нет тестового контрагента; счёт с чужим GUID.

## 10. Одной фразой

В 1С для теста обмена нужны: **дерево категорий**, **≥25 SKU** (15 цветных + 10 обычных), **15 оттенков 5×3 с HEX**, атрибуты, цены/остатки/коробки, **2 контрагента**, рабочий **`post_orders`**, **счёт (`bill`) на заказ**. Акт сверки — к контрагенту; претензии и заявки — не документы обмена. Live-статусы и UI документов ЛК на этом срезе **не обещать**.
