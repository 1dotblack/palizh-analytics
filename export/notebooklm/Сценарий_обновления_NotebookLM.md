# Сценарий обновления корпуса в NotebookLM (Palizh)

Ограничение: до **50** источников на ноутбук (Standard). Текущий bundle — **15** файлов с запасом на рост (новые блоки добавляются в сборку в `tools/build_notebooklm_bundle.rb` или отдельным YAML без дубликатов).

**Одной командой CLI** (пересборка `bundle/` + удаление всех источников блокнота + повторная загрузка файлов из `bundle/`):

```bash
./tools/sync_notebooklm.sh
```

ID блокнота и название задаются в **[NOTEBOOK_TARGET](NOTEBOOK_TARGET)** (фиксированное для этого репозитория). При смене целевого блокнота обновите `NOTEBOOK_ID` в этом файле.

Требования: установлен **`notebooklm`** в `PATH`, выполнен **`notebooklm login`** (или сохранённые куки), **`python3`**.

При загрузке OpenAPI в NotebookLM по CLI: после сборки используйте **`bundle/09_openapi_mvp_merged.md`**, **`10…12` с расширением `.md`** — внутри fenced-блок `yaml` лежит тот же текст, что и в соседнем **`*.yaml`**. Сырые **`*.yaml`** как «файл» часто дают **HTTP 400**; **`sync_notebooklm.sh`** загружает только **`bundle/*.md`**.

При ручном пошаговом обновлении см. ниже.

## 1. Регулярное обновление (вручную)

1. Зафиксируйте изменения в репозитории или просто сохраните файлы локально.
2. При необходимости обновите merged OpenAPI (рабочая директория — **`Техническая часть/`**):

```bash
ruby tools/merge_openapi_mvp.rb
```
3. Пересоберите выгрузку:  
   `ruby tools/build_notebooklm_bundle.rb`
4. Проверьте **`export/notebooklm/MANIFEST.md`**: коммит, дата сборки.

### В интерфейсе NotebookLM или через CLI (`notebooklm-py`)

NotebookLM воспринимает **повторную загрузку с тем же названием источника** как новый объект (зависит от продукта). Надёжный способ без накопления мусора:

1. Откройте ноутбук **Palizh** (или переименуйте старый в `Palizh — архив YYYY-MM-DD`, если хотите сохранять снимки).
2. Для каждого файла из `bundle/`: удалите источник с тем же смыслом (UI) или выполните `notebooklm source delete <id>` после `notebooklm source list`, если используете CLI.
3. Добавьте все файлы заново из обновлённого `bundle/`.

При CLI и сценарии «замена без ошибок имени»: можно завести **фиксированные заголовки** и удалять через `notebooklm source delete-by-title "Exact Title"` — см. навык NotebookLM (`~/.cursor/skills/notebooklm/SKILL.md`).

**Быстрое добавление всей папки (bash):**

```bash
cd export/notebooklm/bundle
for f in *.md *.yaml; do notebooklm source add "./$f" --json || true; done
```

После добавления подождите индексирование: `notebooklm source list --json`, пока все источники в статусе `ready`, либо `notebooklm source wait` по ID.

### Авторизация CLI

См. `notebooklm login`, контекст ноутбука: `notebooklm use <notebook_id>` или флаги `-n` / `--notebook` для параллельных задач.

## 2. Крупное изменение набора блоков

Если приближаетесь к лимиту **50**:

- Не добавляйте отдельно `openapi_client_mvp.yaml` и `openapi_1c_inbound_mvp.yaml`, если уже есть **`09_openapi_mvp_merged.yaml`**.
- Не дублируйте **`входящие/1c-http-openapi.yaml`** с **`Техническая часть/1c-http-openapi.yaml`** — в bundle уже **`11_1c_http_openapi.yaml`**.
- Объединяйте новые мелкие `.md` в существующие корпуса (правка `build_notebooklm_bundle.rb`) вместо отдельного источника на каждый файл.

При необходимости разнесите содержание на **два ноутбука**, например: «Palizh — ТЗ» и «Palizh — Интервью и план».

## 3. Контроль версий

Источник правды всегда **Git**. Ноутбук NotebookLM — **производная**. В `MANIFEST.md` сохраняется короткий хеш коммита и время сборки; при сомнении сверяйте с историей Git.
