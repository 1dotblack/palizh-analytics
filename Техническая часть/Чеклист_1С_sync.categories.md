# Чеклист 1С: выгрузка категорий витрины (`sync.categories`)

**Дата:** 2026-07-09  
**Для кого:** разработчик 1С, ответственный за обмен с B2B-платформой Palizh  
**Цель:** корректно заполнить дерево категорий на витрине через `POST /exchange` → `sync.categories` и связать товары с категориями.

**Контекст приёмки (стенд `palizh.nutnetdev.ru`, 2026-07-09):** платформа принимает пакеты, `GET /api/categories` отвечает **200**, но в ответе **~122 корневые записи без детей**, названия похожи на **товары**, а не на группы витрины («Клеи и герметики» → «Герметики»). HTTP-контракт и фронт **согласованы**; проблема — в **составе и иерархии данных из 1С**.

## 1. Что должно получиться на платформе

После успешной выгрузки:

1. **`GET /api/categories`** (публичный API) возвращает **дерево**: корневые категории + **один уровень** вложенных `children`.
2. На главной витрины фронт берёт первые 9 корневых категорий и строит ссылки `/categories/{slug}`.
3. **Slug** генерирует платформа из `name` и иерархии (`родитель/ребёнок`), в JSON **не передаётся**.
4. Категории с `isArchived: true` **не показываются** гостям и клиентам.
5. Категории с полем `counterparties` видны **только** указанному контрагенту (+ общие категории без этого поля).

## 2. Что выгружать и чего не выгружать

| Выгружать в `sync.categories` | Не выгружать в `sync.categories` |
|-------------------------------|----------------------------------|
| **Папки / группы** дерева витрины (навигационные категории) | Элементы номенклатуры (товары) |
| Записи с осмысленными **групповыми** названиями («Краски», «Грунтовки») | Строки с артикулами, «№…», полным наименованием SKU |
| GUID, стабильный во времени | Временные или суррогатные ID без связи с `Ref` 1С |
| Иерархию через `parentGuid` | Плоский список из сотен «корней» без детей (если в 1С дерево глубже одного уровня) |

**Не путать:**

| Сущность | Событие | Назначение |
|----------|---------|------------|
| Категория витрины | `sync.categories` | Навигация, фильтр листинга |
| Тип (вид) номенклатуры | `sync.product-types` | Краски, герметики как **тип** товара |
| Товар | `sync.products` | Карточка SKU; поле `parentGuid` = GUID **категории**, не типа |

## 4. Контракт `POST /exchange`

### 4.1. Транспорт

| № | Проверка | Статус |
|---|----------|--------|
| 1 | `POST https://<стенд>/exchange` (TLS 1.2+) | ☐ |
| 2 | Тело: `{ "event": "sync.categories", "payload": [ ... ] }` | ☐ |
| 3 | Подпись HMAC-SHA256 сырого тела в `X-Palizh-Signature` | ☐ |
| 4 | Успех платформы: **HTTP 202** (обработка асинхронно в очереди) | ☐ |
| 5 | Повторная отправка того же пакета не ломает данные (идемпотентность по `guid`) | ☐ |

### 4.2. Поля элемента `payload[]`

| Поле JSON | Тип | Обяз. | Правило | Статус |
|-----------|-----|-------|---------|--------|
| `guid` | uuid | да | Уникальный GUID категории в 1С | ☐ |
| `parentGuid` | uuid \| null | да | `null` только у **корня**; у дочерней — GUID родителя из **того же** пакета/справочника | ☐ |
| `name` | string | да | Краткое **групповое** имя для меню витрины, не название товара | ☐ |
| `isArchived` | boolean | да | `true` — скрыть на витрине | ☐ |
| `counterparties` | uuid | нет | Если категория только для одного B2B-клиента. Имя поля именно **`counterparties`** (не `counterpartiesGuid`!) | ☐ |

**Пример (канон):**

```json
{
  "event": "sync.categories",
  "payload": [
    {
      "guid": "8b0c9c9a-1f9f-4edb-8d6b-8a3b2d2c0c1a",
      "parentGuid": null,
      "name": "Клеи и герметики",
      "isArchived": false
    },
    {
      "guid": "9b0c9c9a-1f9f-4edb-8d6b-8a3b2d2c0c1b",
      "parentGuid": "8b0c9c9a-1f9f-4edb-8d6b-8a3b2d2c0c1a",
      "name": "Герметики",
      "isArchived": false
    }
  ]
}
```

### 4.3. Типичные ошибки в JSON

| Ошибка | Последствие на платформе |
|--------|--------------------------|
| В `sync.categories` уходят **товары** вместо папок | На витрине «категории» с названиями SKU |
| У всех записей `parentGuid: null` | Плоский список сотен корней, нет меню-дерева |
| `parentGuid` ссылается на несуществующий `guid` | Ребёнок не попадёт под родителя (FK / пропуск связи) |
| Перепутано `counterparties` и `counterpartiesGuid` | Категория не привяжется к контрагенту |
| Отправка до `sync.counterparties` при заполненном `counterparties` | Предупреждение в логе; `counterparty_guid` не проставится |

## 5. Порядок и режим выгрузки

| № | Правило | Статус |
|---|---------|--------|
| 1 | **Первичная заливка** — полный срез дерева категорий | ☐ |
| 2 | **Далее** — дельты при изменении в 1С (инициатор — 1С) | ☐ |
| 3 | Рекомендуемый порядок каталога: `sync.product-attributes` → `sync.product-types` → `sync.product-type-characteristics` → **`sync.categories`** → `sync.products` → `sync.stocks` → `sync.prices` | ☐ |
| 4 | Перед `sync.products`: все `parentGuid` товаров должны уже существовать как `guid` в `sync.categories` | ☐ |
| 5 | При полной перезаливке категорий — согласовать с платформой влияние на slug и SEO-ссылки | ☐ |

---

## 6. Связь с товарами (`sync.products`)

В `sync.products` поле **`parentGuid`** на платформе сохраняется как привязка товара к категории (`category_guid`).

| № | Проверка | Статус |
|---|----------|--------|
| 1 | `parentGuid` в товаре = GUID **листовой или ближайшей** папки-категории в дереве витрины | ☐ |
| 2 | Этот GUID совпадает с записью из `sync.categories`, а не с `typeGuid` | ☐ |
| 3 | Товар не дублируется в `sync.categories` | ☐ |
| 4 | Для эксклюзивного товара — `counterpartiesGuid` в **товаре**; для эксклюзивной **категории** — `counterparties` в **категории** | ☐ |

## 7. Самопроверка перед демо

Выполнить на тестовом стенде после выгрузки:

### 7.1. Пакет 1С

| № | Критерий | Ожидание | Факт | OK |
|---|----------|----------|------|-----|
| 1 | Число элементов в `payload` | Порядок величины **десятки**, не сотни SKU | | ☐ |
| 2 | Доля записей с `parentGuid != null` | > 0, если в 1С есть подкатегории | | ☐ |
| 3 | Нет имён вида «№1234 … Palizh» в корневых категориях | 0 таких в корне | | ☐ |
| 4 | Все `parentGuid` разрешаются в тот же массив | 100% | | ☐ |

### 7.2. API платформы

```http
GET /api/categories
Accept: application/json
```

| № | Критерий | Ожидание | Факт | OK |
|---|----------|----------|------|-----|
| 1 | HTTP-код | 200 | | ☐ |
| 2 | Формат | `{ "data": [ { "id", "name", "slug", "children": [...] } ] }` | | ☐ |
| 3 | Есть корни с непустым `children` | ≥ 1, если в 1С есть 2-й уровень | | ☐ |
| 4 | `slug` у дочерней категории | Содержит `/` (например `klei-i-germetiki/germetiki`) | | ☐ |
| 5 | Архивные категории | Не возвращаются | | ☐ |

### 7.3. Сквозной сценарий

| № | Шаг | OK |
|---|-----|-----|
| 1 | Открыть главную витрины — блок категорий показывает **группы**, не товары | ☐ |
| 2 | Клик по категории ведёт на `/categories/{slug}` без 404 | ☐ |
| 3 | `GET /api/products?categorySlug={slug}` возвращает товары этой ветки | ☐ |

## 8. Диагностика текущего расхождения (стенд 2026-07-09)

Если снова видите картину «122 корня, 0 детей, названия как у товаров»:

1. Выгрузить из 1С **первые 5 элементов** фактического `sync.categories` (JSON).
2. Сверить: это `IsFolder = true` или элементы номенклатуры?
3. Проверить заполнение `Parent` / `parentGuid` в исходнике 1С.
4. Убедиться, что отдельный регламент выгрузки **не подменяет** категории списком номенклатуры.
5. После исправления — повторить п. 7 и приложить скрин `GET /api/categories` (фрагмент) к отчёту.
