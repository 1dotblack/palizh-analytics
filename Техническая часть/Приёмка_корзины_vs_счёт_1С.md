# Приёмка: корзина платформы vs счёт 1С

**Статус:** рабочий чек-лист (MVP)  
**Связь:** [ЧТЗ 01 §4.2.4](../ЧТЗ/01_процесс_оформления_заказа.md), [Принятые_решения_API_интеграция_1С.md](Принятые_решения_API_интеграция_1С.md) §4, [openapi_mvp_cart_checkout_orders.md](openapi_mvp_cart_checkout_orders.md) §5.3.

**Назначение:** критерии интеграционной приёмки **до выставления счёта** — сумма заказа на платформе после `POST /orders` должна быть согласуема со счётом 1С. При расхождении для клиента источник истины — **счёт 1С** (ЧТЗ 01 §4.3).

---

## 1. Предусловия

- На stage загружены тестовые `sync.products` (`unitsPerBox`), `sync.prices` (`amount`, `amountPerBox`, при необходимости `discountedAmount*`).
- Контрагент с соглашением, по которому известны виды цен (`RETAIL` / `WHOLESALE` / `BOX`) и персональная скидка % (если применимо).
- Backend пересчитывает корзину по **варианту A** (локально из `sync.prices`, без online-запроса в 1С).

---

## 2. Тест-кейсы по строке корзины

| ID | Условия | quantity | Ожидание `packagingMode` | Проверка `lineTotal` |
|----|---------|----------|--------------------------|----------------------|
| T1 | `unitsPerBox=15`, есть `amountPerBox` и `amount` | 15 | `multiple` | `round(1 × pricePerBox, 2)` |
| T2 | то же | 20 | `mixed` | `round(1 × pricePerBox, 2) + round(5 × pricePerPiece, 2)` |
| T3 | то же | 5 | `non_multiple` | `round(5 × pricePerPiece, 2)` |
| T4 | `unitsPerBox` null или 0 | любое | `not_applicable` | `round(qty × pricePerPiece, 2)` |
| T5 | скидка % на розницу | 20 | `mixed` | `pricePerBox` / `pricePerPiece` из `discountedAmount*` |
| T6 | опт `WHOLESALE` | 20 | по кратности | скидка % **не** применяется |
| T7 | вид цены `BOX` в `sync.prices` | кратно | `multiple` | скидка % **не** применяется к `BOX` |

`pricePerBox` = `discountedAmountPerBox` ?? `amountPerBox`; `pricePerPiece` = `discountedAmount` ?? `amount`. Округление: **RUB, 2 знака, round half up** на каждом слагаемом и на `lineTotal`. `unitPrice` = `round(lineTotal / quantity, 2)` — для UI, не для сверки с 1С.

---

## 3. Тест-кейсы по заказу

| ID | Проверка |
|----|----------|
| O1 | Итог заказа на платформе = сумма `lineTotal` строк + доставка (если есть) на момент оформления. |
| O2 | После обработки в 1С сумма **счёта** совпадает с O1 **или** расхождение документировано (правила 1С по округлению на уровне документа). |
| O3 | При намеренном расхождении (изменение цены в 1С между корзиной и счётом) клиенту показывается сумма из **счёта**. |

**Допуск:** зафиксировать на stage с командой 1С (типично ±0,01 ₽ на строку из-за порядка округления в 1С). Если 1С считает иначе — приоритет **подстройки формулы платформы** под печатную форму 1С (ЧТЗ 01 §4.2.4), не наоборот.

---

## 4. Артефакты для прогона

| Артефакт | Обязательность |
|----------|----------------|
| JSON фикстуры `sync.prices` / `sync.products` для T1–T7 | Да |
| Скрин/дамп корзины API (`CartItem`) | Да |
| Печатная форма **счёта** или строки заказа 1С после `post_orders` | Да для O2 |
| Отдельный PDF-прайс клиенту | **Нет** — клиент видит `lineTotal` в UI; выгрузка таблицы цен **только по запросу** (вне MVP-потока корзины). |

---

## 5. Порядок прогона

1. Залить фикстуры каталога/цен на stage.
2. Авторизоваться B2B-пользователем контрагента.
3. Для каждого T1–T7: добавить позицию в корзину, сверить `lineTotal`, `packagingMode`, `fullBoxesCount`, `remainderQuantity` в ответе API.
4. Оформить заказ (O1), дождаться счёта из 1С (O2–O3).
5. Зафиксировать расхождения в тикете интеграции (#18).

---

## 6. Открыто

- Точный допуск в копейках — согласовать с 1С на первом прогоне.
- Поведение при одновременной смене цены в 1С во время оформления — отдельный сценарий (редкий; post-MVP или регламент поддержки).
